# AGENTS.md

Instructions for AI coding agents (Claude Code, Cursor, Aider, etc.) working
in this repo. Read this before making changes.

## What this project is

`charged/tailwindphp` is a pure-PHP port of the Tailwind CSS v4 compiler.
The bulk of `src/` (the ~80 procedural files matching JS source layout) is
a 1:1 port from `tailwindlabs/tailwindcss`. The OO surface (`src/Tailwind.php`,
`src/TailwindCompiler.php`, `src/Plugin/`, `src/Minifier/`, `src/Normalizer/`,
`src/Exception/`, `src/classnames.php`) is original PHP-native code.

**The split matters.** Different rules apply to each side.

## Hard rules — never break these

1. **Do not restructure the procedural port files.** Files like `src/index.php`,
   `src/apply.php`, `src/variants.php`, `src/utilities.php`, `src/candidate.php`,
   `src/css-parser.php`, etc. mirror specific `.ts` files in upstream Tailwind.
   Maintainers sync upstream changes by diffing the JS source against the
   corresponding `.php` file. Reorganising them — even "improving" them —
   makes every future upstream sync archaeology.

   If you must modify a procedural file, keep the structure recognisable and
   add a `@port-deviation:<category>` header annotation explaining why.

2. **Do not bump versions or push tags autonomously.** Tags are one-way and
   downstream consumers anchor against them. Always confirm with the user
   before running `git tag`, `git push --tags`, or `gh release create`.

3. **Do not modify `src/theme.cache.php` by hand.** It's generated by
   `php bin/build-theme-cache.php`. If `resources/theme.css` changes, regenerate
   the cache; `tests/ThemeCacheTest.php` will fail otherwise.

4. **Do not modify `tests/fixtures/*/expected.css` by hand.** If a fixture's
   expected output legitimately changes, regenerate it (delete the file and
   run the test suite — `FixtureParityTest` auto-seeds missing baselines —
   then review the diff before committing).

## Soft rules — defaults you can override with good reason

- New classes go under PSR-4 paths: `src/<Namespace>/<Class>.php` matching
  `TailwindPHP\<Namespace>\<Class>`. PSR-4 autoload entries are listed in
  `composer.json` — add a new entry if introducing a new top-level namespace.
- Class files use `final class` unless you have a specific reason to allow
  subclassing.
- Throw typed exceptions from `TailwindPHP\Exception\` (or `\LogicException`
  for genuinely internal invariant violations). Never raw `\Exception`.
- Test files use PHPUnit conventions: `snake_case` test method names, one
  test class per file (but inline test-fixture classes are fine, see
  `tests/PluginsTest.php`).

## Definition of done — before declaring work complete

Run these and confirm they pass:

```bash
composer test     # phpunit, all green
composer lint     # phpcs, all green
composer analyse  # phpstan, all green
```

If you added a new feature, also add at least one test for it. If you fixed
a bug, add a regression test. If you added a fixture under `tests/fixtures/`,
re-run the suite so `expected.css` gets seeded.

## Changelog — what the user actually wants automated

The user wants AI to manage `CHANGELOG.md` so they don't have to think about
it. Follow [Keep a Changelog 1.1.0](https://keepachangelog.com/en/1.1.0/) format.

### When work lands on `main`

Add an entry under the `## [Unreleased]` section. Use the correct category:

| Category | Use for |
|---|---|
| `### Security` | Vulnerability fixes |
| `### Added` | New features (public API, options, files) |
| `### Changed` | Behaviour changes that are not breaking |
| `### Deprecated` | APIs marked for future removal |
| `### Removed` | APIs / files that are gone |
| `### Fixed` | Bug fixes (no API change) |

Write entries from the consumer's perspective, not the maintainer's:

- ❌ `Refactored CssMinifier to use a tokeniser`
- ✅ `CSS minifier no longer corrupts \`content: "0px"\` or `url(./0px.png)`
   strings during zero-unit stripping.`

Reference PRs where relevant (`[#12](.../pull/12)`). Lead with the user-visible
behaviour change, follow with one short clause of mechanism if helpful.

If the `## [Unreleased]` section says `_Nothing yet._`, remove that line
when adding the first real entry.

### When the user asks to cut a release

1. Pick the version (ask if unclear — see "Version bumping" below).
2. Promote `## [Unreleased]` to `## [X.Y.Z] - YYYY-MM-DD`. Add a new empty
   `## [Unreleased]` above it with `_Nothing yet._`.
3. Add link references at the bottom of the file:
   ```
   [Unreleased]: https://github.com/charged-labs/tailwindphp/compare/vX.Y.Z...HEAD
   [X.Y.Z]: https://github.com/charged-labs/tailwindphp/releases/tag/vX.Y.Z
   ```
   …and update the `[Unreleased]` link to use the new version as the compare base.
4. Open a PR titled `CHANGELOG: promote Unreleased → X.Y.Z`. Include the proposed
   GitHub Release body in the PR description.
5. **Stop. Do not tag.** Wait for the user to merge the PR.
6. After they confirm the merge, **then** propose the tag/release commands —
   still don't run them without explicit go-ahead.

## Version bumping (SemVer)

Tags use a `v` prefix (`v1.0.0`, not `1.0.0`).

| Change shape | Bump |
|---|---|
| Bug fix, no API change | `1.0.0` → `1.0.1` (PATCH) |
| New feature, backwards-compatible | `1.0.0` → `1.1.0` (MINOR) |
| Breaking change | `1.0.0` → `2.0.0` (MAJOR) |
| Pre-release of next version | `1.1.0-beta1` → `1.1.0-beta2` → `1.1.0` |

**Pre-release suffixes** (`-beta1`, `-rc1`) are appropriate when the next
release introduces deprecations or substantial new surface and you want
field validation before consumers pin against it as stable.

**Things that look like minor changes but are actually breaking:**
- Adding a required argument to an existing function
- Tightening an existing function's return type (e.g. `?string` → `string`)
- Changing the *shape* of a returned array
- Renaming a public class or method (deprecation alias mitigates this)
- Removing a `@deprecated` API (always MAJOR)
- Raising the minimum PHP version

When in doubt, ask the user — version bumps cannot be undone.

## Release workflow checklist

After CHANGELOG promotion PR merges:

```bash
git checkout main && git pull --ff-only
git tag -a vX.Y.Z -m "vX.Y.Z — <one-line summary>"
git push origin vX.Y.Z
gh release create vX.Y.Z --title "vX.Y.Z" --verify-tag --notes-file <(...release body...)
# For pre-releases, add --prerelease
```

Packagist auto-syncs new tags within ~30 seconds if the GitHub App is installed
(it is — verify at https://github.com/apps/packagist).

The same process is written up for humans under "Releasing" in `README.md`.
If you change how releases work, change both — they describe one process for
two audiences, and a reader following the stale one ships a bad tag.

## Things to know about the codebase

- **Procedural-port files use array-shaped AST nodes.** `['kind' => 'at-rule',
  'name' => '...', 'nodes' => [...]]`. There's a deferred refactor to type
  these as classes — when/if it lands, follow the phased plan documented in
  the original prompt (ask the maintainer for it).
- **`bin/regen-fixtures.sh`** regenerates `tests/fixtures/*/expected.css`
  against the upstream JS compiler (requires Node + `npx`). Run after upstream
  Tailwind syncs to catch divergence.
- **`bin/build-theme-cache.php`** regenerates `src/theme.cache.php` from
  `resources/theme.css`. Run after any change to the theme.
- **Plugin DI is per-compile** as of v1.0.0-beta1 — `tw::generate(['plugins'
  => [...]])` rather than the deprecated `registerPlugin()` singleton.
- **PHPStan baseline** is in `phpstan-baseline.neon`. Regenerate against PHP
  8.3 (matches CI). New findings on the OO surface should be fixed, not
  baselined; new findings in procedural files can be baselined.
